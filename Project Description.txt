MARSWAY - COMPLETE PROJECT DESCRIPTION
=======================================

Project type: Interactive Mars GIS, exploration simulator, and mission-planning decision-support tool
Challenge theme: Interplanetary Survival Guide: Martian Map
Application: Browser-based React and TypeScript platform


IMPORTANT SAFETY STATEMENT
--------------------------

MarsWay is an educational prototype. It makes Mars science, planetary mapping,
route trade-offs, and emergency-oriented decision support easier to understand.
It is not flight-certified navigation software and must not be used as the sole
source for real astronaut, rover, spacecraft, or mission operations.


1. EXECUTIVE SUMMARY
--------------------

MarsWay combines a real Mars map, planetary places, NASA data context, mission
records, environmental information, route analysis, a 3D globe, an astronaut
EVA simulation, and an offline assistant in one application.

The platform is designed around a practical mission question:

    If a person or rover needs to travel from one Martian location to another,
    what is there, what can go wrong, which route is preferable, and why?

The application does not treat distance as the only decision factor. It also
considers terrain, slope, soil trafficability, hazard exposure, dust risk,
transport mode, crew assumptions, science value, and estimated travel time.
The interface explains the result instead of presenting an unexplained green
or red line.


2. THE PROBLEM
--------------

Mars data is distributed across planetary nomenclature catalogues, orbital
imagery, elevation products, thermal imagery, mineral datasets, rover records,
environmental instruments, and mission archives. A feature name alone does not
explain whether a crew or rover can reach it. A direct line between two points
does not show slope, loose soil, dust, terrain trafficability, pressure, or
time.

MarsWay brings these pieces together:

    place identity
        -> science and environmental context
        -> route endpoints
        -> candidate route generation
        -> hazard and safety explanation
        -> local multilingual assistance

This makes the project useful for education, demonstrations, mission-planning
scenarios, and emergency-oriented offline workflows.


3. PROJECT OBJECTIVES
---------------------

1. Make Mars science visual and understandable.
2. Connect place names with real surface and mission context.
3. Demonstrate that the shortest path is not always the safest or fastest
   operational path.
4. Show environmental and human-survivability constraints before route choice.
5. Keep basic assistance available when a network or remote AI provider is
   unavailable.
6. Preserve transparency by distinguishing observation, history, derivation,
   modeling, and simulation.


4. COMPLETE USER FLOW
---------------------

4.1 Select a location

The user searches for or selects a location such as Jezero Crater, Gale Crater,
Olympus Mons, Valles Marineris, Utopia Planitia, or a mission landing site.
Selection can happen through the map, Places dock, Mission Explorer, or Search.

4.2 Define a scientific objective

The user may ask the system to support an objective such as finding clay-bearing
delta deposits, inspecting hydrated minerals, comparing a crater rim and floor,
reaching a rover site, or avoiding steep and low-traction terrain.

4.3 Inspect the dossier

The selected place can expose official identity, feature type, coordinates,
elevation, regional context, geology, water/ice indicators, atmosphere, human
safety, rover suitability, mission relationship, imagery, and science tools.

4.4 Inspect the environment

Before route planning, the user can inspect gas composition, pressure,
temperature, wind, dust, precipitation, radiation context, elevation, slope,
soil, and terrain suitability. Each value is presented with a provenance label.

4.5 Plan a route

The user clicks Route Plan, selects START and FINAL on the map, chooses EVA/foot
or rover travel, configures crew assumptions, selects an objective, and runs
Check Route.

4.6 Compare the result

The application presents shortest, safest, and science-priority candidates with
distance, time, maximum slope, soil, terrain, hazards, dust risk, and detour
explanation. The selected route is drawn on the same map using numbered
waypoints and endpoint markers.

4.7 Ask MarsWay

The user can ask a question in English, Bangla Unicode, or Banglish. The local
assistant reads the active location and route context when available and gives
a bounded response from local knowledge and deterministic rules.


5. FLAT MAP / 2D GIS
--------------------

The Flat Map is the main operational workspace. It uses Leaflet with a Mars
geographic coordinate system.

Capabilities:

- pan, zoom, mouse wheel, touch pinch, and coordinate readout;
- Mars compass, North/East/South/West-up orientation, and reset-to-north;
- Mars scale bar and radius context;
- searchable place and mission catalogue;
- fly-to and selected-place dossiers;
- Viking true-colour, THEMIS infrared, and MOLA shaded-relief layers;
- mission, rover, lander, landing-site, region, and traverse overlays;
- START and FINAL route selection;
- elevation point inspection and MOLA transects;
- distance and bearing measurement;
- atmosphere, pressure, temperature, dust, and MOLA availability overlays;
- science and environmental cards.

The map uses progressive disclosure. Global scale shows important labels only;
regional and local detail appears as the user zooms. This keeps the planet
readable rather than covering it with overlapping text.

5.1 Map loading and fallback

NASA public tiles may be slow, incomplete, rate-limited, or temporarily
unavailable. MarsWay immediately places a bundled Viking surface image beneath
the remote layer. NASA tiles progressively load on top of it. Slow or failed
tiles therefore do not produce large black rectangles. The fallback is muted,
darkened, desaturated, and slightly blurred so that loading looks intentional
and professional instead of like a bright orange placeholder.

5.2 Rotated map behaviour

The compass supports four cardinal orientations. When the map rotates, the
canvas is scaled in a controlled way so the rectangular global Mars texture does
not expose empty corners. Labels and controls remain readable. Map click and
drag calculations apply the inverse rotation and scale so visual position and
geographic position remain aligned.


6. 3D GLOBE
-----------

The 3D Globe is a Three.js planetary overview.

It provides:

- camera orbit and zoom;
- directional sunlight and Mars atmosphere;
- mission, rover, and lander markers;
- Phobos and Deimos context;
- orbit/space presentation;
- Earth-scale comparison;
- handoff to the 2D map and EVA view.

The globe answers “where is this on Mars?” The 2D map and route engine answer
“what is around it?” and “how should it be approached?”


7. ASTRONAUT EVA VIEW
---------------------

The EVA view represents an astronaut standing at a local surface position. It
is intentionally not a zoomed-out global map while the astronaut is walking.

The EVA experience includes:

- first-person camera and helmet-inspired HUD;
- real Mars reconnaissance inset;
- heart rate, oxygen, suit pressure, altitude, heading, and EVA timer;
- compass, target reticle, and local target card;
- geology/mineral composition and LIBS-style scan;
- sample collection interaction;
- W/A/S/D movement and visible 6-DOF controller;
- forward hazard scan and change-heading guidance;
- tactical map handoff.

Movement changes the local EVA position. The forward scan checks the corridor
ahead against terrain, slope, soil, dust, and hazard context. It may report
smooth terrain, caution, or a recommended heading change. These are modeled
educational guidance messages, not autonomous navigation guarantees.


8. ROUTE PLANNING ENGINE
------------------------

8.1 Route states

    IDLE -> SELECT START -> SELECT FINAL -> READY -> CHECKED -> ACTIVE ROUTE

Selecting START does not claim that a route is safe. Selecting FINAL enables
analysis but does not replace Check Route. The active route is updated only
after a result is calculated and accepted.

8.2 Route objectives

Shortest:
    Prioritizes minimum distance and expected travel time.

Safest:
    Gives stronger penalties to hazards, steep slopes, poor traction, unstable
    terrain, dust exposure, and other operational concerns.

Science:
    Allows a controlled detour toward a science target, resource proxy, or
    geologically important corridor.

8.3 Route inputs

- START and FINAL coordinates;
- Mars great-circle distance;
- modeled elevation and slope;
- soil trafficability;
- terrain suitability;
- hazard proximity and hazard type;
- local dust-risk probability;
- transport mode;
- crew configuration;
- science/resource objective;
- speed and time penalties.

8.4 Route outputs

- direct path distance;
- selected route distance;
- estimated travel time;
- maximum slope and elevation change;
- soil and terrain scores;
- hazard count and severity;
- direct-corridor warning;
- safer bypass recommendation;
- shortest/safest/science comparison;
- route line and numbered waypoints;
- hazard areas and endpoint markers;
- Fit to Map and Safe Corridor Active actions.

8.5 Transparent cost model

    total cost = distance cost
               + time cost
               + slope cost
               + soil/terrain cost
               + hazard cost
               + dust-risk cost
               - science/resource value

The weights change according to the chosen objective. A safe route may be
longer but still preferred because it avoids a steep scarp, low-traction soil,
or modeled dust exposure.

8.6 Route status meanings

Nominal:
    No major issue was detected by the current local model.

Caution:
    A moderate concern exists, such as lower traction, dust, or slope.

Concern:
    A meaningful terrain, soil, slope, environmental, or route penalty exists.

Hazard:
    The corridor intersects a strong modeled hazard or operational constraint.

These labels describe model output and are not field-certified safety decisions.


9. ENVIRONMENTAL AND HUMAN SAFETY PANELS
----------------------------------------

Atmosphere:
    Thin CO2-dominated air, pressure, and gas composition.

Water/Ice:
    Surface hydration, ice indicators, hydrated minerals, and resource proxies.

Human:
    Suit requirement, pressure danger, radiation context, and EVA warnings.

Rover:
    Terrain suitability, soil trafficability, and movement implications.

Weather:
    Historical or modeled temperature, wind, dust, and precipitation.

Geology:
    Mineral composition, rock type, surface unit, and science target context.

Elevation:
    MOLA Areoid reference, slope, profiles, and pressure relationship.


10. OFFLINE AI / ASK MARSWAY
----------------------------

10.1 Why it is offline

In a Mars emergency or field demonstration, communication may be delayed,
intermittent, low-bandwidth, or unavailable. A public AI service may also be
down, unavailable, or require credentials. MarsWay therefore keeps its basic
assistant local.

The local assistant is:

- independent of Gemini and other AI API keys;
- private because questions are not sent to a remote model;
- fast and predictable;
- bounded and easier to test;
- available whenever the local application and datasets are available;
- able to use current place and route context.

10.2 How it works

    question
      -> text normalisation
      -> English/Bangla/Banglish matching
      -> local intent classification
      -> location/route context lookup
      -> bounded answer

Supported topics include atmosphere, gases, human survival, EVA, places,
elevation, soil, terrain, hazards, route safety, route time, rover suitability,
and general application help.

10.3 Offline boundaries

Offline AI means supported assistant questions do not need a remote AI call. It
does not mean that every new NASA tile, external photograph, archive page, or
live feed can be loaded without a network. The service worker caches the shell,
local assets, and previously requested resources.

12. PROVENANCE AND TRANSPARENCY
-------------------------------

Observed:
    Direct image, measurement, archive record, or instrument observation.

Historical:
    Recorded by an earlier mission or mapping campaign; not live telemetry.

Derived:
    Calculated from coordinates, geometry, or catalogue relationships.

Modeled:
    Produced by a transparent scientific or engineering approximation.

Simulated:
    Generated for visualization, education, or scenario exploration.

Examples:

- An official feature name is source-backed.
- Great-circle distance is derived.
- Pressure estimated from elevation is modeled.
- Route time adjusted for slope and soil is modeled.
- Helmet effects and dust overlays are simulated presentation layers.

14. API AND INTERNAL DATA FLOW
------------------------------

Feature search:

    search input -> /api/features -> local catalogue -> result -> map fly-to

Elevation:

    coordinate -> elevation model -> elevation/pressure -> science card/route

Route:

    START + FINAL + options -> /api/routes/plan -> candidates + safety result

Assistant:

    question + context -> /api/ask-marsway -> local intent matcher -> answer

The Express API does not call an external AI provider. It exposes local data
and deterministic calculations to the browser.

17. LIMITATIONS
--------------

- Not flight-certified and not suitable as the sole operational navigation
  source.
- MOLA-scale elevation cannot resolve every small obstacle.
- HiRISE and CRISM coverage is targeted, not uniform.
- Soil, terrain, weather, radiation, pressure, dust, and route time may be
  historical, derived, modeled, or simulated.
- The route engine does not replace lidar, AutoNav, field sampling, or crew
  judgement.
- Public NASA imagery depends on network availability and service limits.
- New uncached imagery and external archives may require a connection.
- The offline assistant only answers supported local questions.
- In-memory mission records may disappear after a server restart.
- 3D/EVA performance depends on WebGL hardware and browser capabilities.

Correct interpretation:

    This is the best result supported by the current local model and datasets,
    not a guarantee that a route is safe in the real Martian environment.


18. PROJECT VALUE
-----------------

MarsWay makes Mars science visual, interactive, and explainable. It shows how
planetary data can support route planning without hiding uncertainty. Its
local-first design is especially important during a network outage or simulated
emergency: users can still search bundled places, inspect local models,
calculate route candidates, compare hazards, and receive basic assistance
without a Gemini key or remote AI service.

20. ROUTE PLANNING DEMONSTRATION EXAMPLE
----------------------------------------

Suppose a user chooses a START near Valles Marineris and a FINAL near Ganges
Chasma.

Step 1 - direct path:
    The engine measures the great-circle corridor and samples its waypoints.

Step 2 - terrain analysis:
    Elevation and slope are estimated along the corridor.

Step 3 - surface analysis:
    Soil trafficability and terrain suitability are evaluated.

Step 4 - hazard analysis:
    Modeled scarps, soft-soil areas, dust concerns, and other hazard regions
    are checked against the corridor.

Step 5 - candidate generation:
    The local router searches nearby alternatives rather than accepting only a
    straight line.

Step 6 - comparison:
    Shortest, safest, and science candidates are ranked using their objective
    weights.

Step 7 - explanation:
    The safety panel explains why a direct route is risky, how much a bypass
    adds, and what risk reduction it provides.

Example presentation:

    Direct shortest: 1376.25 km, crosses a steep scarp, hazard status.
    Safer bypass:    1376.82 km, avoids the scarp, nominal status.
    Trade-off:       +0.57 km for a lower modeled slope and hazard exposure.

The numbers above are illustrative. The actual interface calculates values from
the selected endpoints and current local model.


21. STATE AND MODAL RULES
-------------------------

The application maintains shared state for:

- primary view mode;
- selected place and selected mission;
- active basemap and scientific overlays;
- map bearing and current map position;
- route endpoints, candidates, and active route;
- mission filters;
- science target and environment context;
- EVA position, heading, telemetry, and scan state;
- open modal and assistant context.

Interaction rules:

1. Selecting a place updates context before opening a dossier.
2. Selecting START never claims the route is safe.
3. Selecting FINAL enables analysis but does not replace Check Route.
4. Opening a modal must not erase the underlying route or location state.
5. Closing a modal returns the user to the same map position where practical.
6. Switching views preserves the selected location where the target view
   supports it.
7. Remote imagery failure must not disable local search, route, science, or
   offline assistant functionality.
8. A route answer must use active route context or clearly say that no route is
   selected.
9. Source-backed and modeled values must remain distinguishable.
10. Responsive modal layouts must keep actions accessible above navigation bars.


22. ROUTE SCORING AND SAFETY ANALYSIS
-------------------------------------

The router and safety analyzer have different responsibilities.

Router:
    Generates and ranks candidate paths using accumulated movement cost and a
    remaining-distance estimate.

Safety analyzer:
    Explains direct-corridor and selected-route hazards, slope, soil,
    terrain, dust, and environmental concerns.

The conceptual cost is:

    cost = distance
         + time
         + slope penalty
         + soil penalty
         + terrain penalty
         + hazard penalty
         + dust penalty
         - science value

Transport mode changes the interpretation. EVA/foot movement receives stronger
penalties for steep or low-traction terrain. Rover movement can tolerate some
conditions differently, but may receive penalties for rocks, scarps, loose soil,
or maneuvering constraints.

Crew configuration can influence expected time, EVA risk context, and mission
explanation. These values are planning assumptions, not measured field data.

24. OFFLINE-FIRST FAILURE BEHAVIOUR
-----------------------------------

If a public NASA tile request is slow:
    The bundled Mars surface remains visible while the tile loads.

If a tile request fails:
    Other tiles can continue loading and the local surface fills the gap.

If the network is unavailable after first load:
    Local search, route calculation, science models, and Ask MarsWay remain
    available from bundled data.

If a remote photograph is unavailable:
    The application keeps the dossier and local science context available.

If an unsupported assistant question is asked:
    The assistant states that the topic is outside its local knowledge rather
    than inventing an answer.

If the browser lacks speech support:
    Text search and text assistant functions remain available.

26. TROUBLESHOOTING GUIDE
-------------------------

Port busy:
    Set PORT to another local port in PowerShell and restart the dev server.

Map black or incomplete:
    Wait for progressive tile loading. The local fallback should appear first.
    If the network is unavailable, continue with the local surface and local
    tools.

Map too slow:
    Use a lower zoom, avoid repeatedly switching basemaps, and allow the
    browser cache to retain previously loaded tiles.

Compass rotation looks wrong:
    Reset to North. The rotated canvas uses controlled scaling and inverse
    pointer mapping; inspect the browser console if the issue persists.

Route looks green unexpectedly:
    Open Details and verify the selected endpoints, objective, transport mode,
    and model assumptions. Nominal means no critical modeled issue was found.

Modal overlaps navigation:
    Close the active panel, resize the browser, and reopen it. Panels use
    responsive max-height and top-level stacking rules.

Assistant does not answer:
    Use a supported question about Mars gas, atmosphere, a place, route safety,
    route time, terrain, soil, rover, or EVA. No API key is needed.


27. FINAL LIMITATIONS
---------------------

MarsWay cannot resolve every small rock, rut, cliff, subsurface void, or local
weather event. MOLA-scale elevation is not lidar. HiRISE and CRISM coverage is
targeted, not uniform. Route time, soil, terrain, dust, radiation, pressure,
and weather may be historical, derived, modeled, or simulated. Public imagery
depends on network service availability. The offline assistant is bounded and
is not a general-purpose chatbot.

The correct interpretation is:

    This is the best result supported by the current local model and datasets,
    not a guarantee that a route is safe in the real Martian environment.
